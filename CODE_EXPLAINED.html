options-arb-scanner · options_rv package · code explained

Forecasting five-day realized variance from option quotes

This page explains the eight modules, how they connect, and what the output numbers mean. It uses a run on the committed data from 10 August 2026.

How to use this

The sections follow the run from configuration to output. Code blocks are unchanged copies from src/options_rv/. The boxes explain the code, define the formulas, show sample data, and point out design choices and failure cases.

The folder name is misleading

The directory is called options-arb-scanner, but the code does not scan for arbitrage. The installed package, options_rv, forecasts realized variance. The name remains from an abandoned idea, described in options-arb-scanner.md and the README. Section 10 lists the no-arbitrage checks a real scanner would need and shows that this code has none of them.

The process in plain English

The code reads two Parquet files: daily closing prices for the exchange-traded fund SPY and daily SPY option quotes. It uses the closes to calculate the target: the price movement over the next five trading days. It turns each day's option quotes into six features, or input variables, then splits time into training, validation, and test periods. A penalized linear regression is fitted on the training period and compared with two simple benchmarks. The run writes four tables, one chart, and a summary file.

01Folder layout and execution

The repository uses a standard src layout. Importable code is in src/options_rv/; the other folders hold inputs, outputs, tests, or documents.

└── blog/generate_charts.py          # reruns the pipeline, freezes charts for an article
Three ways to run it

1. Command line. uv run python -m options_rv.cli --config config.toml --output-dir outputs/demo_run. The installed options-rv console script is also declared in pyproject.toml under [project.scripts].
2. Notebook. notebooks/options_rv_pipeline_demo.ipynb calls the same package functions one at a time and shows each intermediate frame.
3. Tests. uv run pytest -q runs 18 unit and integration tests with small synthetic inputs in a temporary folder.

Why the database code is separate

Only io/clickhouse_export.py imports clickhouse_connect, and only scripts/refresh_raw_from_clickhouse.py imports that module. The normal path never uses it. With data/raw/ present, a fresh clone runs the study without a network, credentials, or a database. This keeps the main workflow self-contained.

The row-count check runs after filtering to required_symbol. With two symbols in one file, the manifest counts both while len(frame) counts one, so the loader rejects the bundle. The data contract assumes one symbol per file.

Limitation

The committed cache is not market data. manifest.json identifies the source as synthetic_local_generation, a deterministic generator used for portability. The results show that the software runs, not how SPY behaves.

04Building the prediction target

build_forward_realized_variance_target — measure the next week's price movement

    # Daily log return and its square are the building blocks for realized variance.
    frame["log_return"] = np.log(
        frame["close"] / frame.groupby("symbol")["close"].shift(1)
    )
    frame["squared_log_return"] = frame["log_return"] ** 2

    # First form a trailing h-return sum ending at each row, then move that sum
    # back by h rows. The value aligned to date t therefore contains returns
    # ending on t+1 through t+h, never the return ending on t.
    forward_sum_squared_returns = frame.groupby("symbol")[
        "squared_log_return"
    ].transform(
        lambda series: (
            series.rolling(window=horizon_days, min_periods=horizon_days)
            .sum()
            .shift(-horizon_days)
        )
    )
In plain words

Realized variance measures how much the price moved. This function calculates it for the next five trading days and attaches it to today, giving the model a target based only on today's information.

What it does

Input: daily closes, a horizon, an annualization factor, and a trailing-window length. Output: one row per symbol-date with forward variance, its logarithm, and trailing 20-day variance. Rows without a complete future window are dropped. Role: supplies the model's label and one of its six features.

The formula

$$r_t=\ln\!\left(\frac{S_t}{S_{t-1}}\right)$$ $$RV_{t,t+h}=\sum_{i=1}^{h}r_{t+i}^{\,2} \qquad \widehat{RV}^{\,\text{ann}}_{t,t+h}=\frac{A}{h}\,RV_{t,t+h}$$ $$y_t=\ln\!\left(\widehat{RV}^{\,\text{ann}}_{t,t+h}\right)$$

$S_t$ is the closing price on trading day $t$. $r_t$ is the log return from the close of day $t-1$ to day $t$, known at the close of day $t$. $h$ is the trading-day horizon, set to 5. $A$ is the annualization factor, set to 252 trading days per year. $RV_{t,t+h}$ is the sum of the next $h$ squared returns. Multiplying by $A/h$ expresses it as a yearly rate, making it comparable with squared implied volatility. $y_t$ is the regression target. Taking its logarithm makes the positive, right-skewed target easier for a linear model to fit; exponentiating the forecast returns it to a positive variance.

The trailing feature

$$\text{trailing}RV^{\text{ann}}_t=\frac{A}{w}\sum_{i=0}^{w-1}r_{t-i}^{\,2}$$

$w$ is the trailing window, fixed at 20 trading days. This uses returns through day $t$, so it is known at the close of day $t$. It is both the sixth regression feature and the persistence benchmark.

There are 522 close observations and 517 label rows. The last five days lack a complete future window and are dropped. The trailing 20-day column starts on 2024-01-30, the 21st session, because the first return is undefined.

Why roll first and shift second

Shifting the returns first and then rolling is off by one: the window at row $t$ would include the return ending on day $t$, which is already known and is not future information. Rolling first builds each backward sum; shifting that sum back $h$ rows attaches it to the date whose future it describes. The repository journal records this bug and its fix on 13 July 2026.

Trap

The shift counts rows, not calendar days. That matches the five-trading-day horizon, but a missing date would stretch the label across the gap. The loader's date-coverage check is what prevents a mis-dated label.

05The six option-surface features

build_option_surface_features — reduce one day's option chain to one row

In plain words

Each day has quotes at several strike prices and expiry dates. This function reduces the chain to five summary numbers, then adds trailing variance as the sixth feature.

What it does

Input: raw option quotes, underlying closes, and the target frame containing trailing variance. Output: one row per symbol-date with six feature columns. Role: the model inputs. The committed cache produces 522 rows, one per trading day.

The building blocks

$$\sigma^{\text{mid}}_i=\frac{\sigma^{\text{bid}}_i+\sigma^{\text{ask}}_i}{2} \qquad m_i=\frac{b_i+a_i}{2} \qquad \text{spread ratio}_i=\frac{a_i-b_i}{m_i}$$ $$\ell_i=\ln\!\left(\frac{K_i}{S_t}\right)$$

The subscript $i$ identifies one quote. $b_i$ and $a_i$ are its bid and ask prices; $m_i$ is their midpoint. $\sigma^{\text{bid}}_i$ and $\sigma^{\text{ask}}_i$ are the implied volatilities supplied with the quote; this code does not calculate them. $K_i$ is the strike, $S_t$ the underlying close, and $\ell_i$ the log-moneyness. It is zero when strike and spot match, negative below spot, and positive above it. The logarithm makes a strike 5 per cent below spot and one 5 per cent above spot roughly symmetric around zero.

The five option features

$$\mathrm{atm\_iv\_30d}_t=\operatorname{mean}\Big\{\sigma^{\text{mid}}_i \;:\; i \in D_{30},\; |\ell_i|=\min_{j\in D_{30}}|\ell_j|\Big\}$$ $$\mathrm{term\_slope}_t=\mathrm{atm\_iv}_t(D_{60})-\mathrm{atm\_iv}_t(D_{30})$$ $$\mathrm{downside\_skew}_t=\sigma^{\text{mid}}_{p^{-}}-\sigma^{\text{mid}}_{p^{0}}$$ $$\mathrm{avg\_spread\_ratio}_t=\frac{1}{n_t}\sum_{i=1}^{n_t}\frac{a_i-b_i}{m_i} \qquad \mathrm{total\_oi}_t=\sum_{i=1}^{n_t}\text{OI}_i$$

$D_{30}$ contains the quotes on day $t$ whose expiry is closest to 30 days; $D_{60}$ does the same for 60. The code chooses from available expiries, so "30-day" means nearest available to 30 days, not exactly 30. $p^{0}$ is the put closest to spot, and $p^{-}$ is the put closest to spot below it; both come from $D_{30}$. $n_t$ is the number of surviving quotes on day $t$. $\text{OI}_i$ is open interest, the number of outstanding contracts. The term slope is missing when the nearest-30 and nearest-60 selections match. The skew is missing if $p^{0}$ and $p^{-}$ are the same contract.

All 20,880 raw quotes pass the quality filter on this cache: zero are rejected. The function returns 522 feature rows, one per trading day.

What the quality filter checks

$$0\le b_i\le a_i,\qquad m_i \gt 0,\qquad 0 \lt \sigma^{\text{bid}}_i\le\sigma^{\text{ask}}_i, \qquad K_i \gt 0,\qquad \text{OI}_i\ge 0,\qquad V_i\ge 0$$

$V_i$ is that contract's traded volume. The option type must be c or p, and every value must be finite. These are single-quote checks: each row is checked alone. The filter does not compare strikes or expiries; see section 10.

Why call and put implied volatilities are averaged

The strike closest to spot usually has one call and one put. Choosing the first row would make the feature depend on file order. Averaging is deterministic, and the two values should agree in a frictionless market because put-call parity links a call and put with the same strike and expiry.

Trap

avg_spread_ratio and total_open_interest use the whole day's chain, not just the 30-day slice. Changing the raw expiries changes these features even when the market does not. Treat them as rough descriptions of this data bundle's liquidity.

Limitation

The input file supplies the implied volatilities; this code does not calculate them. It cannot know which interest rate, dividend assumption, or pricing model produced them. A change in the supplier's convention would change the features without triggering a check.

build_chronological_split_masks — split early and late rows with a gap

    ...

In plain words

Time-ordered data must be split by time, not shuffled. This function assigns the first 60 per cent to training, the next 20 per cent to validation, and the last 20 per cent to test. It then removes the five rows before each boundary.

What it does

Input: a frame with trade_date, two fractions, and a purge size. Output: one label per row in the caller's original order: train, validation, test, or purged. Role: controls which periods enter each calculation.

Why the gap equals the horizon

The label at row $t$ uses returns from $t+1$ through $t+h$. Two labels $h$ or fewer rows apart therefore share a return: $$\{t+1,\dots,t+h\}\cap\{s+1,\dots,s+h\}\ne\varnothing \quad\Longleftrightarrow\quad |t-s| \lt h$$

$t$ and $s$ are row positions, and $h$ is the horizon in rows. Rows closer than the horizon have overlapping labels. Removing the last $h$ rows before a boundary leaves the closest surviving row exactly $h$ positions away, so the two periods share no return. With $h=5$, this removes five rows before validation and five before test.

The fractions apply to row counts, not calendar time. They coincide here because the panel has one row per trading day and no gaps.

Why labels keep the caller's order

The function sorts by date internally, then writes labels to a Series with the caller's index. The result can be assigned to the panel without realignment. Sorting the caller's frame would silently change its order.

Trap

The default is purge_gap_rows=0. Forgetting the horizon removes no gap and contaminates validation and test scores. That was the notebook's bug; see Fixes applied.

07Two benchmarks

In plain words

Before trusting a model, compare it with two simple forecasts: "next week will resemble the last month" and "the option market already contains the answer."

def compute_persistence_baseline(feature_target_frame: pd.DataFrame) -> pd.Series:
    # Persistence uses the same trailing variance feature the ridge model sees.
    return feature_target_frame["trailing_annualized_variance_20d"].astype(float)


def compute_atm_iv_baseline(feature_target_frame: pd.DataFrame) -> pd.Series:
    # Variance is volatility squared under the standard Black-Scholes convention.
    atm_iv = feature_target_frame["atm_iv_30d"].astype(float)
    return atm_iv * atm_iv
The formulas

$$f^{\text{persistence}}_t=\text{trailing}RV^{\text{ann}}_t \qquad f^{\text{atm}}_t=\left(\mathrm{atm\_iv\_30d}_t\right)^2$$

$f_t$ forecasts annualized variance for the window after day $t$. Persistence reuses the trailing 20-day annualized variance. The second forecast squares implied volatility, which is quoted as annualized standard deviation, to obtain annualized variance. Both forecasts use the same units as the label.

Sample data
in — panel row for 2024-01-30 
trailing_annualized_variance_20d  5.2899e-05

out — the two forecasts, against the truth

0.179617 squared is 0.032262. In this synthetic cache, implied volatility is near 18 per cent per year while the price path moves at about 0.44 per cent per year. The at-the-money benchmark is therefore about three orders of magnitude too high on every row.

Limitation

Comparing 30-day implied variance with 5-day realized variance assumes expected annual variance is similar across those horizons. The methodology document states this assumption. Here the comparison is also invalid because the synthetic implied volatilities do not match the price path.

08The model

In plain words

It puts the six features on a common scale, fits a linear relationship to the log of next week's variance using training rows only, and predicts every row for later scoring.

What it does

Input: the panel, split labels, feature columns, target column, and penalty strength. Output: a RidgeTrainingResult containing the fitted scikit-learn pipeline, a prediction table, and a coefficient table. Role: the repository's only fitted model.

The formula, in three steps

Step 1, standardize using training rows only: $$z_{j,t}=\frac{x_{j,t}-\bar{x}^{\text{train}}_j}{s^{\text{train}}_j}$$ Step 2, the objective the fit minimizes: $$\hat{\beta}=\arg\min_{\beta}\;\sum_{t\in\text{train}} \left(y_t-\beta_0-\sum_{j=1}^{p}\beta_j z_{j,t}\right)^{2} \;+\;\alpha\sum_{j=1}^{p}\beta_j^{2}$$ Step 3, back to variance units for scoring: $$f^{\text{ridge}}_t=\exp\!\left(\hat{\beta}_0+\sum_{j=1}^{p}\hat{\beta}_j z_{j,t}\right)$$

$x_{j,t}$ is feature $j$ on day $t$; there are $p=6$ features. $\bar{x}^{\text{train}}_j$ and $s^{\text{train}}_j$ are feature $j$'s mean and standard deviation, computed on the training rows only. That prevents test-period information from entering the fit. $z_{j,t}$ is the feature in training-standard-deviation units. $y_t$ is the log annualized forward variance from section 4. $\beta_0$ is the intercept and $\beta_j$ the slope for feature $j$. $\alpha$ is the ridge penalty, fixed at 1.0. The extra $\alpha\sum\beta_j^2$ term pulls slopes toward zero, which stabilizes them when features move together. $f^{\text{ridge}}_t$ is the forecast on the variance scale.

Two coefficients are zero because the synthetic generator keeps term slope at 0.027 and downside skew at 0.012 every day. A constant column has no standard deviation, so scikit-learn sets its scale to 1. The standardized column is then all zeros, and the ridge penalty sets its coefficient to zero. The cause is the data, not the model.

Why the scaler is inside the pipeline

Putting the scaler and regressor in one Pipeline and calling fit on training rows makes both learn from training data only. Scaling the full panel before splitting would leak test-period information into the training features. The pipeline prevents that mistake.

Trap

model.predict runs on every row, including the ten purged rows. The metric table ignores them and loops only over train, validation, and test. predictions.csv still contains the purged rows. Recomputing a score without filtering by split produces a different result.

Limitation

The penalty $\alpha$ is fixed at 1.0 in pipeline/offline_research.py; the validation split does not tune it. Also, the fit minimizes squared error in log space. Exponentiating its output gives roughly the conditional median on the variance scale, not the conditional mean, so it does not minimize squared error for the level target. The methodology document records this issue and leaves it uncorrected.

09Scoring the forecasts

def qlike(
    actual_variance: pd.Series, predicted_variance: pd.Series, epsilon: float = 1e-12
) -> float:
    actual = actual_variance.to_numpy(dtype=float)
    # Floor predicted variance so log and ratio terms stay finite.
    predicted = np.maximum(predicted_variance.to_numpy(dtype=float), epsilon)
    return float(np.mean(np.log(predicted) + (actual / predicted)))
The three formulas

$$\text{RMSE}=\sqrt{\frac{1}{n}\sum_{t=1}^{n}\left(y^{\text{lev}}_t-f_t\right)^{2}} \qquad \text{MAE}=\frac{1}{n}\sum_{t=1}^{n}\left|y^{\text{lev}}_t-f_t\right|$$ $$\text{QLIKE}=\frac{1}{n}\sum_{t=1}^{n}\left(\ln f_t+\frac{y^{\text{lev}}_t}{f_t}\right)$$

$n$ is the number of rows in one split. $y^{\text{lev}}_t$ is realized annualized forward variance on the level scale. $f_t$ is a model's forecast, floored at $10^{-12}$ so the logarithm and division stay finite. RMSE means root mean squared error; MAE means mean absolute error. Both use annualized-variance units, and lower is better. QLIKE is a loss for variance forecasts. It uses the ratio $y/f$ rather than a difference, so under- and over-forecasting are not treated symmetrically. Lower is better. QLIKE can be negative because of $\ln f_t$.

Trap

All three functions convert inputs to NumPy arrays and compare by position. Two Series with different orders therefore produce a wrong number without a warning. This code slices both from the same frame, so they align; the functions themselves do not check.

10The arbitrage conditions this code does not test

The folder name is not the implementation

The folder suggests a static arbitrage scanner. None of the four conditions below appear in src/: there is no put-call parity, vertical-spread, butterfly, or calendar test. The quote filter in section 5 checks each quote alone and never compares two quotes. The conditions below show exactly what is missing.

Put-call parity — not implemented

$$C_t(K,T)-P_t(K,T)=S_t e^{-qT}-K e^{-rT}$$

$C_t(K,T)$ and $P_t(K,T)$ are European call and put prices with the same strike $K$ and expiry $T$, measured in years. $S_t$ is the underlying spot price. $r$ is the continuously compounded annual risk-free rate, and $q$ the continuously compounded dividend yield. A difference larger than transaction costs would imply a riskless profit. Testing this needs a discount curve and dividend forecast, neither of which is in the raw data. Any parity claim from these files would therefore be unsupported.

Vertical spread bounds — not implemented

$$0\;\le\;C_t(K_1,T)-C_t(K_2,T)\;\le\;(K_2-K_1)\,e^{-rT}\qquad\text{for }K_1 \lt K_2$$

$K_1$ and $K_2$ are two strikes on expiry $T$, with $K_1$ lower. The left inequality says a lower-strike call cannot cost less than a higher-strike call. The right inequality limits how quickly the price may fall as strike rises. A violation is a riskless spread trade.

Butterfly convexity — not implemented

$$C_t(K_1,T)-2\,C_t(K_2,T)+C_t(K_3,T)\;\ge\;0 \qquad\text{for equally spaced }K_1 \lt K_2 \lt K_3$$

The three strikes are evenly spaced, so $K_2-K_1=K_3-K_2$. The expression buys one call at $K_1$, sells two at $K_2$, and buys one at $K_3$. Its payoff cannot be negative at expiry, so its price cannot be negative today. Equivalently, call price must be convex in strike. Stale or poorly interpolated quotes often violate this condition.

Calendar spread bound — not implemented

$$C_t(K,T_1)\;\le\;C_t(K,T_2)\qquad\text{for }T_1 \lt T_2$$

The calls share strike $K$, and $T_1$ is the nearer expiry. Without dividends, more time cannot reduce a call's value, so the longer-dated call must cost at least as much. With dividends, the comparison must use forward moneyness rather than raw strike; otherwise an ex-dividend date can create a false alarm.

Why bid and ask matter here

Each condition concerns tradeable prices. A real test buys at the ask and sells at the bid, so it must use the correct side for each leg. Midpoints can show violations that no one can trade. This repository uses midpoints to describe the surface; that is insufficient for an arbitrage claim.

run_offline_research — eleven steps in order

What it does

Input: a raw folder, an output folder, and the three settings from config.toml. Output: four DataFrames in memory and six files on disk. Role: the central workflow. The command line and blog chart script call it; the notebook follows it step by step.

12The one-time database refresh

In plain words

This optional script connects to a ClickHouse database, downloads fresh SPY option and price data, and rewrites the three files in data/raw/. No other workflow uses it.

What it does

Input: connection details from the environment or command line, a symbol, and a date range. Output: two Parquet files and a new manifest.json. Role: refreshes the offline cache. It requires network access and credentials.

The filter the query applies at the source

$$7\;\le\;\mathrm{expiry\_date}-\mathrm{trade\_date}\;\le\;90\ \text{calendar days}, \qquad \mathrm{expiry\_date} \gt \mathrm{trade\_date}$$

This keeps the export small. It also guarantees that the 60-day feature is available while excluding longer expiries, fixing the term-structure range visible to the features.

Why parameterized queries

The symbol and dates are passed as ClickHouse query parameters ({symbol:String}, {start_date:Date}) instead of pasted into the SQL string. This is safer and lets the server check their types.

Not run for this page

This is the only repository component without sample data here. Running it needs a ClickHouse host with a firstrate.options table and working credentials. Everything else on this page was executed.

18If someone points at a line

QuestionAnswer
"Where exactly is look-ahead prevented?"The label applies .shift(-h) to a completed backward sum, so day $t$ uses only returns from $t+1$ to $t+h$. The scaler and regressor fit on training rows only. purge_gap_rows=horizon_days also removes five rows before each boundary, preventing shared returns.
"Why does the target module also produce a feature?"The trailing 20-day variance uses the same returns as the label. Computing it once keeps the returns and annualization identical; the feature module joins it instead of recomputing it.
"Why 497 rows and not 522?"522 trading days minus 5 without a complete future window minus 20 without a complete trailing window. 522 − 5 − 20 = 497.
"What happens if I set horizon_days = 10?"The label sums ten future returns, column names change from ..._5d to ..._10d, and the purge becomes ten rows at each boundary. The panel also loses five more rows at the end.
"Why is the term-slope coefficient exactly zero?"The synthetic generator fixes the feature at 0.027 on all 522 days. Its standard deviation is zero, so scikit-learn uses scale 1; the standardized column is all zeros and the penalty sets its coefficient to zero. Real data would not have this property.
"Is the ridge model any good?"No. Persistence beats it on validation and test by all three measures. Ridge wins only on training, which indicates it is fitting noise.
"Why is QLIKE negative?"The $\ln f_t$ term is negative because variance is around $2\times10^{-5}$ and its logarithm is about $-10.8$. QLIKE ranks models; its absolute level is not meaningful.
"Can I trust these numbers?"Yes as evidence that the software runs: an actual run produced them and the notebook reproduces them. No as evidence about SPY: the manifest says the inputs are synthetic.
"How long does it take?"A few seconds for a full run; roughly 1.5 seconds for all 18 tests. The feature builder's per-day Python loop is the slowest part and runs 522 times.
"Does it need a database?"No on the normal path. Only scripts/refresh_raw_from_clickhouse.py connects, and the command line, notebook, and tests never call it.
"Where would a real arbitrage scanner go?"Beside _filter_valid_quotes, as a stage that groups quotes by expiry and compares strikes. It would need a discount curve, dividend assumptions, and bid and ask prices. None of these are present.

19Limitations

The data is synthetic

manifest.json gives the source as synthetic_local_generation. The numbers on this page show that the software works. Two features are constant, implied volatilities do not match the price path, and the path is too smooth to support conclusions about the options market.

The name does not match the code

The folder name suggests a chain scanner, but the code forecasts variance. The README and guide files explain this, while the folder and note file still suggest otherwise.

Quote timing is unchecked

The raw files record only a trade date, not a time. The code cannot tell whether an option snapshot came before or after the underlying close. If it came after, the features contain information the label should not use. The methodology document notes this; no code fixes it.

Validation is not used for tuning

The ridge penalty is fixed at 1.0. The validation split does not choose features, a horizon, or a window; it is only reported on. The test split is therefore the only untouched segment.

Limited scope

There is no cross-symbol check, horizon sweep, rolling refit, or confidence interval. Three models scored on 100 test rows cannot separate skill from luck, and the code does not try.

No trading model

Nothing converts a variance forecast into a position, hedge, or profit and loss. There are no bid-ask costs, margin, or capacity limits. The output compares forecasts, not trading strategies.
