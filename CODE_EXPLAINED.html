options-arb-scanner · options_rv package · code explained

Forecasting five-day realized variance from option quotes

What this repository actually contains, how the eight modules feed each other, and what each number in the output tables means. Every figure on this page came from running the code on the committed data on 10 August 2026.

How to use this

Sections follow execution order, from the configuration file to the written tables. Code blocks are copied unedited from the files under src/options_rv/. Coloured boxes carry plain-English summaries, formulas with every symbol defined, real sample data, design reasons, and traps.

The folder name is misleading

The directory is called options-arb-scanner, but nothing in the code scans for arbitrage. The installed package is options_rv, and it forecasts realized variance. The name is a leftover from an abandoned idea, recorded in options-arb-scanner.md and admitted in the README. Section 10 sets out the no-arbitrage conditions a real scanner would test and shows plainly that none of them appear in this code.

The process in plain English

The code reads two small Parquet files: daily closing prices for the exchange-traded fund SPY, and a daily snapshot of option quotes on SPY. From the closes it builds the thing to be predicted: how much the price actually moved over the next five trading days. From the option quotes it builds six numbers per day that describe the shape of the option market that day. It then splits the timeline into an early training stretch, a middle validation stretch, and a late test stretch, fits a simple penalized linear regression on the training stretch only, and compares it against two dumb benchmarks. Finally it writes four tables, one chart, and a short summary file.

01Folder layout and what runs what

The repository is a standard src layout. Everything importable lives in src/options_rv/; everything else is inputs, outputs, tests, or documents.

└── blog/generate_charts.py          # reruns the pipeline, freezes charts for an article
The three ways to run it

1. Command line. uv run python -m options_rv.cli --config config.toml --output-dir outputs/demo_run. There is also an installed console script named options-rv, declared in pyproject.toml under [project.scripts].
2. Notebook. notebooks/options_rv_pipeline_demo.ipynb calls the same package functions one at a time so you can see each intermediate frame.
3. Tests. uv run pytest -q runs 18 unit and integration tests that build their own small synthetic inputs in a temporary folder.

Why the database code is quarantined

Only io/clickhouse_export.py imports clickhouse_connect, and only scripts/refresh_raw_from_clickhouse.py imports that module. Nothing on the normal path touches it. That means a fresh clone with data/raw/ present runs the whole study with no network, no credentials, and no database. This is the single most useful structural decision in the repository.

SettingWhat changing it does
raw_dirPoints the loader at a different bundle of Parquet files. A relative value is now read relative to the folder holding config.toml (see Fixes applied).
symbolFilters both raw files. Any symbol absent from either file makes the loader raise RawDataValidationError. The committed cache only holds SPY.
horizon_daysChanges three things at once: how many future returns the label sums, the column names (annualized_forward_variance_5d becomes ..._10d), and the size of the purge gap at each split boundary. Larger values shrink the panel, because the last horizon_days rows have no complete future window.
annualization_factorScales every variance number, both label and trailing feature, by the same constant. It changes the level of RMSE and MAE but not which model wins.

In plain words

load_config reads the four settings out of the text file, falls back to a sensible default for anything missing, and works out where the data folder really is.

What it does

Input: a path to a TOML file. Output: an OfflineResearchConfig dataclass with four fields, frozen so nothing downstream can edit it. Role: the only place in the package that reads configuration from disk.

Trap

Every value has a default, so a typo in a key name silently gives you the default rather than an error. Writing horizon_day = 10 (missing the "s") leaves the horizon at 5 and the run looks fine.

03Reading and checking the raw cache

load_raw_data — read two files, refuse anything unexpected

In plain words

It opens the two Parquet files and the manifest, then runs a long list of checks. If anything is missing, mismatched, or too short, it stops with a message that names the problem instead of letting a broken assumption leak into the maths downstream.

What it does

Input: a folder path, a required symbol, and a minimum number of trading days. Output: a RawDataBundle holding the two sorted, date-normalized DataFrames and the parsed manifest dictionary. Role: the boundary between untrusted files and trusted in-memory frames. Everything after this point assumes clean inputs.

Trap

The row-count check runs after the frames have been filtered down to required_symbol. If you ever put two symbols in one file, the manifest count will describe the whole file while len(frame) describes one symbol, and the loader will reject a perfectly good bundle. The data contract quietly depends on one symbol per file.

The weakness, stated honestly

The committed cache is not market data. manifest.json records its own source as synthetic_local_generation: a deterministic generator wrote it so the repository would run anywhere. Every number produced downstream is evidence that the software works, not evidence about SPY.

04Building the thing to predict

build_forward_realized_variance_target — how much the price moves next week

    # Daily log return and its square are the building blocks for realized variance.
    frame["log_return"] = np.log(
        frame["close"] / frame.groupby("symbol")["close"].shift(1)
    )
    frame["squared_log_return"] = frame["log_return"] ** 2

    # First form a trailing h-return sum ending at each row, then move that sum
    # back by h rows. The value aligned to date t therefore contains returns
    # ending on t+1 through t+h, never the return ending on t.
    forward_sum_squared_returns = frame.groupby("symbol")[
        "squared_log_return"
    ].transform(
        lambda series: (
            series.rolling(window=horizon_days, min_periods=horizon_days)
            .sum()
            .shift(-horizon_days)
        )
    )
In plain words

Realized variance is a plain measure of how bumpy the price path was. This function measures the bumpiness of the next five trading days and attaches that number to today, so a model built from today's information has something to aim at.

What it does

Input: the daily close table, a horizon, an annualization factor, and a trailing window length. Output: one row per symbol-date with the forward variance, the logarithm of the forward variance, and the trailing 20-day variance. Rows without a complete future window are dropped. Role: supplies both the label the model is scored against and one of the six features.

The formula

$$r_t=\ln\!\left(\frac{S_t}{S_{t-1}}\right)$$ $$RV_{t,t+h}=\sum_{i=1}^{h}r_{t+i}^{\,2} \qquad \widehat{RV}^{\,\text{ann}}_{t,t+h}=\frac{A}{h}\,RV_{t,t+h}$$ $$y_t=\ln\!\left(\widehat{RV}^{\,\text{ann}}_{t,t+h}\right)$$

$S_t$ is the closing price on trading day $t$. $r_t$ is the log return earned from the close of day $t-1$ to the close of day $t$; it is known at the close of day $t$. $h$ is the horizon in trading days, set to 5. $A$ is the annualization factor, set to 252, the usual count of trading days in a year. $RV_{t,t+h}$ is the sum of the next $h$ squared returns, in units of squared daily return. Multiplying by $A/h$ rescales it to a yearly rate, which is why it is comparable to a squared implied volatility. $y_t$ is the column the regression is fitted on: taking the logarithm turns a strictly positive, right-skewed quantity into something a linear model handles better, and guarantees the forecast stays positive after exponentiating.

The trailing feature, same idea pointed backwards

$$\text{trailing}RV^{\text{ann}}_t=\frac{A}{w}\sum_{i=0}^{w-1}r_{t-i}^{\,2}$$

$w$ is the trailing window, fixed at 20 trading days in the pipeline. This one uses returns up to and including day $t$, so it is fully known at the close of day $t$. It is used twice: as the sixth regression feature, and on its own as the persistence benchmark.

Why roll first and shift second

The obvious way to write this is to shift the returns forward and then take a rolling sum. That is off by one: the window ending at row $t$ would then include the return that ended on day $t$ itself, which is already known and is not part of the future. Rolling first produces a completed backward sum at every row, and shifting that finished sum back by exactly $h$ rows lands it on the date whose future it describes. The repository journal records this as a real bug that was found and fixed on 13 July 2026.

Trap

The shift is by rows, not by calendar days. That is deliberate: five trading days is the intended horizon. But it also means a gap in the input dates silently stretches the label across that gap. The loader's requirement that the option file cover every underlying date is the only thing standing between you and a silently mis-dated label.

05The six option-surface features

build_option_surface_features — squeeze a day's option chain into one row

In plain words

On any given day there are dozens of option quotes at different strikes and expiry dates. This function boils that whole chain down to five numbers that describe its shape, then joins on the trailing-variance column to make six.

What it does

Input: the raw option quote table, the underlying close table, and the target frame that carries the trailing-variance column. Output: one row per symbol-date with six feature columns. Role: the predictors. On the committed cache this is 522 rows, one per trading day.

The building blocks

$$\sigma^{\text{mid}}_i=\frac{\sigma^{\text{bid}}_i+\sigma^{\text{ask}}_i}{2} \qquad m_i=\frac{b_i+a_i}{2} \qquad \text{spread ratio}_i=\frac{a_i-b_i}{m_i}$$ $$\ell_i=\ln\!\left(\frac{K_i}{S_t}\right)$$

The subscript $i$ indexes one option quote. $b_i$ and $a_i$ are the bid and ask prices in dollars; $m_i$ is their midpoint. $\sigma^{\text{bid}}_i$ and $\sigma^{\text{ask}}_i$ are the implied volatilities that come with the quote, already supplied in the data rather than solved for here. $K_i$ is the strike price, $S_t$ the closing price of the underlying that day, and $\ell_i$ the log-moneyness: it is zero when the strike equals the spot price, negative below it and positive above it. Using the logarithm makes a strike 5 per cent below spot and one 5 per cent above spot roughly symmetric around zero.

The five option features

$$\mathrm{atm\_iv\_30d}_t=\operatorname{mean}\Big\{\sigma^{\text{mid}}_i \;:\; i \in D_{30},\; |\ell_i|=\min_{j\in D_{30}}|\ell_j|\Big\}$$ $$\mathrm{term\_slope}_t=\mathrm{atm\_iv}_t(D_{60})-\mathrm{atm\_iv}_t(D_{30})$$ $$\mathrm{downside\_skew}_t=\sigma^{\text{mid}}_{p^{-}}-\sigma^{\text{mid}}_{p^{0}}$$ $$\mathrm{avg\_spread\_ratio}_t=\frac{1}{n_t}\sum_{i=1}^{n_t}\frac{a_i-b_i}{m_i} \qquad \mathrm{total\_oi}_t=\sum_{i=1}^{n_t}\text{OI}_i$$

$D_{30}$ is the set of quotes on day $t$ whose days-to-expiry is closest to 30; $D_{60}$ the same for 60. Both are picked from whatever expiries exist that day, so "30-day" means "nearest available to 30 days", not exactly 30. $p^{0}$ is the put whose strike is closest to spot; $p^{-}$ is the put whose strike is closest to spot from below, both inside $D_{30}$. $n_t$ is the number of surviving quotes on day $t$, across all expiries and strikes. $\text{OI}_i$ is open interest, the number of contracts outstanding. The term slope is set to missing when the nearest-30 and nearest-60 selections land on the same expiry, and the skew is set to missing when $p^{0}$ and $p^{-}$ turn out to be the same contract.

What the quality filter actually checks

$$0\le b_i\le a_i,\qquad m_i \gt 0,\qquad 0 \lt \sigma^{\text{bid}}_i\le\sigma^{\text{ask}}_i, \qquad K_i \gt 0,\qquad \text{OI}_i\ge 0,\qquad V_i\ge 0$$

$V_i$ is the day's traded volume for that contract, and the option type must be one of the two recognized codes, c or p. Every quantity must also be finite. These are all single-quote checks: each row is judged alone. Nothing compares one strike against another or one expiry against another. See section 10.

Why call and put implied volatilities get averaged

At the strike closest to spot there are usually two quotes, one call and one put. Picking whichever one appears first in the file would make the feature depend on row order, which is not a property of the market. Averaging them is deterministic and, in a market without frictions, the two should agree anyway because a call and a put at the same strike and expiry are linked by put-call parity.

Trap

avg_spread_ratio and total_open_interest are computed over the whole day's chain, every expiry and strike, not over the 30-day slice. Change the set of expiries in the raw file and these two features move even though nothing about the market changed. They are best read as coarse liquidity descriptors of the data bundle, not clean market signals.

The weakness, stated honestly

The implied volatilities are taken from the input file as given. Nothing here computes them, so nothing here knows what interest rate, dividend assumption, or pricing model produced them. If the supplier's convention changes, the features change and no check in this repository would notice.

In plain words

Time-ordered data must be split by time, never shuffled. This function labels the earliest 60 per cent of rows as training, the next 20 per cent as validation, the last 20 per cent as test, and then throws away the five rows just before each boundary.

What it does

Input: any frame with a trade_date column, two fractions, and a purge size. Output: one label per row, in the caller's original row order, taking one of four values: train, validation, test, purged. Role: the leakage control. Nothing else in the code decides who sees what.

Why the gap has to be exactly the horizon

The label at row $t$ is built from returns on days $t+1$ through $t+h$. Two labels $h$ or fewer rows apart therefore share at least one return: $$\{t+1,\dots,t+h\}\cap\{s+1,\dots,s+h\}\ne\varnothing \quad\Longleftrightarrow\quad |t-s| \lt h$$

$t$ and $s$ are two row positions and $h$ the horizon in rows. Read it as: if two rows are closer together than the horizon, their two answers are partly the same numbers. Deleting the last $h$ rows on the training side of a boundary makes the closest surviving training row and the first validation row exactly $h$ apart, so no return appears on both sides. With $h=5$ this removes five rows before validation and five before test, ten in all.

Note that the fractions are applied to row counts, not to calendar time. Because the panel has one row per trading day with no gaps, the two happen to coincide here.

Why labels come back in the caller's order

The function sorts by date internally to decide who belongs where, but writes the answers into a Series carrying the caller's own index, so it can be assigned straight onto the panel with no realignment. Sorting the caller's frame instead would have been a silent trap.

Trap

The default is purge_gap_rows=0. A caller who forgets to pass the horizon gets a split with no gap and quietly contaminated validation and test scores. That is precisely the bug that was sitting in the notebook; see Fixes applied.

07Two benchmarks

In plain words

Before believing a model, check it beats the two laziest possible forecasts: "next week will be like the last month", and "the option market already told me".

def compute_persistence_baseline(feature_target_frame: pd.DataFrame) -> pd.Series:
    # Persistence uses the same trailing variance feature the ridge model sees.
    return feature_target_frame["trailing_annualized_variance_20d"].astype(float)


def compute_atm_iv_baseline(feature_target_frame: pd.DataFrame) -> pd.Series:
    # Variance is volatility squared under the standard Black-Scholes convention.
    atm_iv = feature_target_frame["atm_iv_30d"].astype(float)
    return atm_iv * atm_iv
The formulas

$$f^{\text{persistence}}_t=\text{trailing}RV^{\text{ann}}_t \qquad f^{\text{atm}}_t=\left(\mathrm{atm\_iv\_30d}_t\right)^2$$

$f_t$ is a forecast of annualized variance for the window starting after day $t$. The persistence forecast simply reuses the trailing 20-day annualized variance. The second converts an implied volatility, which is quoted as an annualized standard deviation, into an annualized variance by squaring it. Both are in the same units as the label, so they can be scored against it directly.

Sample data
in — panel row for 2024-01-30 
trailing_annualized_variance_20d  5.2899e-05
atm_iv_30d                        0.179617
out — the two forecasts, against the truth 
actual        1.9779e-05
persistence   5.2899e-05    2.7x too high
atm_iv        3.2262e-02    1600x too high

0.179617 squared is 0.032262. On this synthetic cache the implied volatility sits near 18 per cent a year while the price path actually moves at about 0.44 per cent a year in volatility terms, so the ATM benchmark is off by three orders of magnitude on every single row.

The weakness, stated honestly

Comparing a 30-day implied variance against a 5-day realized variance only makes sense if the market's expected variance per year is roughly flat between those two horizons. The methodology document says so explicitly. On the committed synthetic cache the comparison is meaningless anyway, because the generator did not make the implied volatilities consistent with the price path it produced.

In plain words

It puts all six features on a common scale, fits a straight-line relationship to the log of next week's variance using only the training rows, and then applies that fitted line to every row so the validation and test rows can be scored.

What it does

Input: the panel, the split labels, the list of feature columns, the target column name, and the penalty strength. Output: a RidgeTrainingResult holding the fitted scikit-learn pipeline, a prediction table with one row per panel row, and a coefficient table. Role: the one model in the repository.

The formula, in three steps

Step 1, standardize using training rows only: $$z_{j,t}=\frac{x_{j,t}-\bar{x}^{\text{train}}_j}{s^{\text{train}}_j}$$ Step 2, the objective the fit minimizes: $$\hat{\beta}=\arg\min_{\beta}\;\sum_{t\in\text{train}} \left(y_t-\beta_0-\sum_{j=1}^{p}\beta_j z_{j,t}\right)^{2} \;+\;\alpha\sum_{j=1}^{p}\beta_j^{2}$$ Step 3, back to variance units for scoring: $$f^{\text{ridge}}_t=\exp\!\left(\hat{\beta}_0+\sum_{j=1}^{p}\hat{\beta}_j z_{j,t}\right)$$

$x_{j,t}$ is feature $j$ on day $t$; $p=6$ features. $\bar{x}^{\text{train}}_j$ and $s^{\text{train}}_j$ are the mean and standard deviation of feature $j$ computed on the training rows only, which is what stops information from the test period leaking backwards. $z_{j,t}$ is the standardized feature, in units of training standard deviations. $y_t$ is the log of annualized forward variance from section 4. $\beta_0$ is the intercept and $\beta_j$ the slope on standardized feature $j$. $\alpha$ is the ridge penalty, fixed at 1.0 in the pipeline; the extra $\alpha\sum\beta_j^2$ term pulls all slopes toward zero, which stabilizes them when features move together. $f^{\text{ridge}}_t$ is the forecast put back on the variance scale.

Two coefficients are zero because the synthetic generator made the term slope constant at 0.027 and the downside skew constant at 0.012 on every single day. A constant column has no standard deviation, so scikit-learn sets its scale to 1 rather than dividing by zero, and the standardized column is identically zero. A column of zeros carries no information and the ridge penalty drives its coefficient to zero. This is the data's fault, not the model's.

Why the scaler lives inside the pipeline

Wrapping the scaler and the regressor in one Pipeline and calling fit on the training rows means the means and standard deviations are learned from training data alone. Standardizing the whole panel first and splitting afterwards would leak information about the test period into the training features. This is one of the most common mistakes in applied forecasting, and the pipeline construct removes the chance of making it.

Trap

model.predict is called on every row, including the ten purged ones. That is harmless because the metric table only loops over train, validation and test. But it means predictions.csv contains ten rows that no reported number uses, and anyone recomputing a score from that file without filtering on the split column will get a slightly different answer.

The weakness, stated honestly

The penalty $\alpha$ is fixed at 1.0 in pipeline/offline_research.py and never tuned. There is a whole validation split whose usual purpose is choosing that number, and it goes unused for that purpose. There is also a retransformation issue: because the fit minimizes squared error in log space, exponentiating gives roughly a conditional median in variance space, not a conditional mean, so it is not the quantity that minimizes squared error against the level target. The methodology document names this problem and does not correct for it.

09Scoring the forecasts

def qlike(
    actual_variance: pd.Series, predicted_variance: pd.Series, epsilon: float = 1e-12
) -> float:
    actual = actual_variance.to_numpy(dtype=float)
    # Floor predicted variance so log and ratio terms stay finite.
    predicted = np.maximum(predicted_variance.to_numpy(dtype=float), epsilon)
    return float(np.mean(np.log(predicted) + (actual / predicted)))
The three formulas

$$\text{RMSE}=\sqrt{\frac{1}{n}\sum_{t=1}^{n}\left(y^{\text{lev}}_t-f_t\right)^{2}} \qquad \text{MAE}=\frac{1}{n}\sum_{t=1}^{n}\left|y^{\text{lev}}_t-f_t\right|$$ $$\text{QLIKE}=\frac{1}{n}\sum_{t=1}^{n}\left(\ln f_t+\frac{y^{\text{lev}}_t}{f_t}\right)$$

$n$ is the number of rows in one split. $y^{\text{lev}}_t$ is the realized annualized forward variance on the ordinary level scale, not the log scale. $f_t$ is the forecast variance from one of the three models, floored at $10^{-12}$ so the logarithm and the division stay finite. RMSE is root mean squared error and MAE is mean absolute error; both are in units of annualized variance, and lower is better. QLIKE is a loss function built for variance forecasting: because a forecast enters as a ratio $y/f$ rather than a difference, halving the forecast is penalized far more than doubling it, which matches how a variance forecast is actually used. Lower is better, and unlike RMSE and MAE it can be negative because of the $\ln f_t$ term.

Trap

All three functions convert to NumPy arrays and compare by position. Pass two Series with different orderings and you get a confidently wrong number with no warning. In this codebase both arguments are always sliced out of the same frame, so they line up, but the functions themselves offer no protection.

10The arbitrage conditions this code does not test

Read this before quoting the folder name

The folder name promises a static arbitrage scanner. To be completely clear: none of the four conditions below appear anywhere in src/. There is no put-call parity test, no vertical spread test, no butterfly test, no calendar test. The quote filter in section 5 checks each quote against itself and never compares two quotes. They are set out here so a reader can see exactly what the gap is.

Put-call parity — not implemented

$$C_t(K,T)-P_t(K,T)=S_t e^{-qT}-K e^{-rT}$$

$C_t(K,T)$ and $P_t(K,T)$ are the prices of a European call and put with the same strike $K$ and the same time to expiry $T$, measured in years. $S_t$ is the spot price of the underlying. $r$ is the risk-free interest rate as a continuously compounded annual rate, and $q$ is the continuously compounded dividend yield of the underlying. If the two sides differ by more than transaction costs, a riskless profit exists. Testing this needs a discount curve and a dividend forecast, neither of which the raw data contains. Two consequences follow: this repository could not run the test even if someone wrote it, and the same missing inputs mean any parity claim built on these files would be unfounded.

Vertical spread bounds — not implemented

$$0\;\le\;C_t(K_1,T)-C_t(K_2,T)\;\le\;(K_2-K_1)\,e^{-rT}\qquad\text{for }K_1 \lt K_2$$

$K_1$ and $K_2$ are two strikes on the same expiry $T$, with $K_1$ the lower one. The left inequality says a call struck lower can never be worth less than a call struck higher: call prices must fall as the strike rises. The right inequality caps how fast they may fall. A violation is a riskless spread trade.

Butterfly convexity — not implemented

$$C_t(K_1,T)-2\,C_t(K_2,T)+C_t(K_3,T)\;\ge\;0 \qquad\text{for equally spaced }K_1 \lt K_2 \lt K_3$$

Three strikes on one expiry, evenly spaced so that $K_2-K_1=K_3-K_2$. The expression on the left is the cost of buying one call at $K_1$, selling two at $K_2$, and buying one at $K_3$. That package can never pay out less than zero at expiry, so it can never cost less than zero today. Equivalently, the call price must be a convex function of the strike. This is the condition most often violated by stale or badly interpolated quotes, and it is the single most useful thing a chain scanner can check.

Calendar spread bound — not implemented

$$C_t(K,T_1)\;\le\;C_t(K,T_2)\qquad\text{for }T_1 \lt T_2$$

Same strike $K$, two expiries with $T_1$ the nearer one. On a non-dividend-paying underlying, more time cannot be worth less, so the longer-dated call must be at least as expensive. With dividends the condition has to be restated on forward-moneyness terms rather than on the raw strike, which is why a careless calendar test throws false alarms around ex-dividend dates.

Why bid and ask matter here and not upstream

Every condition above is an inequality on tradeable prices. To claim a violation you must buy at the ask and sell at the bid, so the correct test uses the bid on whatever you sell and the ask on whatever you buy. Using midpoints will manufacture violations that no one can actually trade. This repository only ever uses midpoints, which is fine for describing the shape of a surface but would be wrong for an arbitrage claim. It is another reason the code should not be described as a scanner.

12The one-time database refresh

In plain words

A separate, optional script that talks to a ClickHouse database, pulls fresh SPY option and price data, and rewrites the three files in data/raw/. Nothing else in the project uses it.

What it does

Input: connection details from the environment or the command line, a symbol, and a date range. Output: the two Parquet files plus a regenerated manifest.json. Role: refills the offline cache. Requires network access and credentials.

The filter the query applies at the source

$$7\;\le\;\mathrm{expiry\_date}-\mathrm{trade\_date}\;\le\;90\ \text{calendar days}, \qquad \mathrm{expiry\_date} \gt \mathrm{trade\_date}$$

This is what keeps the exported file small. It also means the 60-day feature is always available while anything longer dated never is, which quietly fixes the shape of the term structure the features can see.

Why parameterized queries

The symbol and dates are passed as ClickHouse query parameters ({symbol:String}, {start_date:Date}) rather than pasted into the SQL string. That is both safer and lets the server type-check the values.

Could not be run for this page

This is the one part of the repository with no sample data on this page. Running it needs a ClickHouse host with a firstrate.options table and working credentials, neither of which is available here. Everything else on this page was executed for real.

18If someone points at a line

QuestionAnswer
"Where exactly is look-ahead prevented?"Three places. The label uses .shift(-h) applied to an already-completed backward sum, so day $t$'s answer contains only returns from $t+1$ to $t+h$. The scaler and regressor sit in one pipeline fitted on training rows only. And purge_gap_rows=horizon_days deletes the five rows before each boundary so no return appears on both sides.
"Why does the target module also produce a feature?"The trailing 20-day variance is built from the same return series as the label. Computing it once, in the same function, guarantees both use identical returns and identical annualization. The feature module joins it on rather than recomputing it.
"Why 497 rows and not 522?"522 trading days, minus 5 with no complete future window, minus 20 with no complete trailing window. 522 − 5 − 20 = 497.
"What happens if I set horizon_days = 10?"Three things at once. The label sums ten future returns instead of five. Every column name changes from ..._5d to ..._10d. And the purge widens to ten rows on each side, so twenty rows leave the evaluation instead of ten. The panel loses five more rows at the end as well.
"Why is the term-slope coefficient exactly zero?"The synthetic generator made that feature constant at 0.027 on all 522 days. A constant has no standard deviation, scikit-learn sets its scale to 1, the standardized column becomes all zeros, and the penalty drives the coefficient to zero. On real data it would not be zero.
"Is the ridge model any good?"No. Persistence beats it on both the validation and the test splits by all three measures. The ridge model only wins on the training split, which is the signature of fitting noise.
"Why is QLIKE negative?"Because of the $\ln f_t$ term. Variance here is around $2\times10^{-5}$, whose logarithm is about $-10.8$. QLIKE is a relative loss for ranking models, not an absolute quantity, so only the comparison between rows matters.
"Can I trust these numbers?"As evidence that the software works, yes: they were produced by an actual run and the notebook reproduces them exactly. As evidence about SPY, no. The manifest says the inputs are synthetic.
"How long does it take?"A few seconds for a full run; roughly 1.5 seconds for all 18 tests. The slowest part is the per-day Python loop in the feature builder, which runs 522 times.
"Does it need a database?"Not for anything on the normal path. Only scripts/refresh_raw_from_clickhouse.py connects, and it is never called by the command line, the notebook, or the tests.
"Where would a real arbitrage scanner go?"Beside _filter_valid_quotes, as a second stage that groups by expiry and compares strikes. It would need a discount curve and dividend assumptions for parity, and bid and ask prices rather than midpoints. None of that exists here.

19Limitations, stated honestly

The data is not real

manifest.json names its own source as synthetic_local_generation. Every number on this page is software evidence. Two features are constant, the implied volatilities are inconsistent with the price path, and the price path is far too smooth. No conclusion about the options market can survive on this input.

The name does not match the code

Anyone finding this folder by its name will expect a chain scanner. The code forecasts variance. The README and the guide files say so, but the folder name, and the note file that inspired it, still point the wrong way.

Nothing checks quote timing

The raw files record a trade date and nothing finer. There is no way to tell whether an option snapshot was taken before or after the underlying close. If option quotes are stamped after the close, the features silently contain a few minutes of information the label should not have seen. The methodology document raises this and no code addresses it.

The validation split is not used for what it is for

The ridge penalty is fixed at 1.0 and never tuned. Nothing selects features, chooses a horizon, or picks a window using the validation split. It is only reported on, which means the test split is the only genuinely untouched segment and the validation numbers add little.

One symbol, one horizon, one model, one seed

There is no cross-symbol check, no robustness sweep across neighbouring horizons, no rolling re-fit, and no confidence interval on any metric. Three models scored on 100 test rows cannot distinguish skill from luck, and the code makes no attempt to.

Costs and tradeability are entirely absent

Nothing here converts a variance forecast into a position, a hedge, or a profit-and-loss. There is no bid-ask cost, no margin, and no capacity. The output is a forecast comparison, and calling it a strategy result would be wrong.
